# Skylark Command V2 Semantic & Evidence Layer

This module makes business definitions, filters, lineage, and evidence quality explicit without moving arithmetic out of the existing deterministic analytics layer.

## Trust boundary

- `src/lib/analytics/**` remains authoritative for business calculations.
- `src/lib/semantic/**` describes canonical metrics/dimensions/joins, invokes existing analytics for verified questions, and records how an answer was produced.
- No metric definition is generated by an LLM.
- No fuzzy business join is permitted.
- Evidence quality is deterministic and descriptive; it is not an AI confidence score.

## Metric registry

Initial semantic registry version `1.0.0` includes:

- `open_pipeline_value`
- `known_won_value`
- `receivables`
- `total_work_order_value`
- `billed_value`
- `collected_value`
- `to_be_billed`
- `open_deal_count`
- `won_deal_count`
- `active_work_order_count`

Each definition names the existing canonical analytics function and canonical output field that owns the value.

## Dimensions

Canonical dimensions are `sector`, `stage`, `client`, `quarter`, `status`, `work_order_status`, `billing_status`, and `collection_status`. Metric/dimension compatibility is validated fail-closed before semantic question execution.

## Exact client join

`deal_to_work_order_by_normalized_client` joins `Deal.normalizedClientKey` to `WorkOrder.normalizedClientKey` by exact equality. Existing `normalizeClientCode` behavior is authoritative: known `COMPANY` variants are normalized deterministically, while unknown formats are not guessed. Fuzzy, embedding, edit-distance, and LLM-assisted joins are explicitly forbidden.

## Answer lineage

`AnswerLineage` can expose:

- metric IDs and semantic versions;
- explicit dimension filters and optional time range;
- source snapshot provider/fetch timestamp;
- source board IDs/names;
- record IDs included and excluded, with exclusion reasons;
- known/unknown value counts per metric;
- exact join path and matched/unmatched key coverage;
- analysis timestamp.

The lineage layer partitions records and reports coverage. It does not sum or otherwise recompute metric values.

## Evidence quality

`assessEvidenceQuality` returns `Strong`, `Moderate`, or `Limited` based on explicit factors:

1. value completeness;
2. snapshot freshness;
3. exact-join coverage;
4. temporal coverage;
5. source-quality issues.

Policy version `1.0.0` uses documented thresholds. The overall class is the worst factor, and every non-strong factor includes a human-readable deterministic reason. No numeric confidence score is produced.

## Why should I trust this result?

`buildTrustResponse` returns a typed `semantic_trust` payload containing the metric definitions, answer lineage, join definitions, evidence quality, deterministic trust boundary, and concrete limitations. Agent/UI layers can render this contract without asking an LLM to invent provenance.

## Verified canonical questions

`executeCanonicalQuestion` supports the first high-value semantic questions:

- `What is open pipeline?`
- `What is won value?`
- `What are receivables?`
- `Which sector has the largest open opportunity?`

These definitions retain the existing `QueryPlan` mappings while invoking the same pure canonical analytics functions used by the product. The semantic layer only selects and annotates authoritative outputs; it does not reimplement business arithmetic.
